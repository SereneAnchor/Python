# AGENTS.md

## 项目分析规则

这是一个 Python 项目。分析项目时，请优先读取少量关键文件，不要一开始扫描整个仓库。

优先阅读顺序：

1. `README.md`
2. `pyproject.toml`、`requirements.txt`、`setup.py`、`setup.cfg` 中存在的文件
3. `src/`、`app/`、`package/`、`main.py` 中存在的入口文件
4. `tests/` 中的关键测试文件
5. 只有在需要时，再读取更具体的模块文件

不要主动读取这些目录或文件：

- `.venv/`
- `venv/`
- `__pycache__/`
- `.pytest_cache/`
- `.mypy_cache/`
- `.ruff_cache/`
- `.git/`
- `dist/`
- `build/`
- `*.egg-info/`
- `node_modules/`
- `logs/`
- `data/` 中的大文件
- `outputs/`
- `checkpoints/`
- `models/`

## 解释项目时的输出要求

当用户说“帮我解释这个项目”“分析一下这个项目”时，请不要逐行解释所有代码，而是按下面结构输出：

1. 项目一句话概括：这个项目主要做什么。
2. 项目目录结构：只列出核心目录和文件，不要列出缓存、虚拟环境、构建产物。
3. 程序入口：说明从哪个文件或函数开始运行。
4. 核心模块：说明主要模块之间的职责关系。
5. 数据流或调用流程：说明请求、数据、任务或命令是如何流转的。
6. 依赖和运行方式：根据配置文件总结安装、运行、测试命令。
7. 新手阅读顺序：告诉用户应该先看哪些文件，再看哪些文件。
8. 风险点或注意事项：指出可能复杂、容易出错或需要进一步确认的地方。

## 修改代码规则

修改代码前，先说明修改计划，不要直接大范围改动。

修改时遵守：

- 优先保持原有代码风格。
- 不要无故重构整个项目。
- 不要改动无关文件。
- 不要删除用户已有注释，除非确实错误。
- 不要把密钥、token、账号信息写入代码。
- 不要修改虚拟环境、缓存、构建产物目录。
- 修改完成后说明改了哪些文件、为什么改、如何验证。

## Python 代码规范

优先遵守项目已有规范。如果项目没有明确规范，则默认：

- 函数和变量使用 `snake_case`。
- 类名使用 `PascalCase`。
- 常量使用 `UPPER_CASE`。
- 尽量添加类型标注。
- 公共函数需要简短 docstring。
- 错误处理要明确，不要裸 `except`。
- 不要在业务代码里随意 `print` 调试信息，优先使用日志。
- 不要随意修改项目依赖，除非用户明确要求。
- 不要把临时调试代码留在最终代码中。

## 常用命令

根据项目实际情况选择命令，不要假设所有命令都存在。

安装依赖可能使用：

```bash
pip install -r requirements.txt
```

或：

```bash
pip install -e .
```

或：

```bash
poetry install
```

运行项目可能使用：

```bash
python main.py
```

或：

```bash
python -m app
```

或：

```bash
uvicorn app.main:app --reload
```

运行测试可能使用：

```bash
pytest
```

代码检查可能使用：

```bash
ruff check .
```

格式化可能使用：

```bash
ruff format .
```

类型检查可能使用：

```bash
mypy .
```

如果命令不确定，请先读取 `README.md` 和项目配置文件，不要猜测。

## 分析优先级

当用户只是想理解项目时，优先分析：

- 入口文件
- 配置文件
- 核心业务模块
- 测试文件
- README 中的运行说明

不要优先分析：

- 自动生成文件
- 缓存文件
- 构建产物
- 大型数据文件
- 第三方库代码
- 虚拟环境目录

## 推荐回答风格

回答要面向初学者，先讲整体，再讲细节。

不要一次性输出过长内容。复杂项目请分阶段分析：

1. 先给整体结构。
2. 再解释入口和主流程。
3. 最后按模块深入。

## 默认工作方式

如果用户没有明确要求修改代码，请只分析，不要修改文件。

如果用户要求修改代码，请先给出修改计划，等待确认后再动手。

如果发现项目结构、运行方式或依赖关系不明确，请先说明不确定点，再继续分析。
